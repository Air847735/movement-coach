# Specification

本文件是研究範圍與成功標準的唯一正式來源，回答「要研究或完成什麼」。安裝、執行與快速使用方式放在 `README.md`；實作方法放在 `architecture.md`。

## Problem and Motivation

- Problem：給定一段人體動作影片，判斷這是什麼動作、動作有什麼問題、需要強化什麼，並給出實際可執行的訓練處方。
- Motivation：現有做法各有硬限制。監督式動作分類需要大量標註影片，換一個動作領域就要重新收集資料；手寫關節角度規則需要逐動作的專家知識，無法擴展；純 VLM 輸出則會生成不存在的動作名稱與作法，無法驗證也無法執行。本專案要驗證的是第三條路：讓 VLM 自由推理，但把最終輸出接地到真實資料庫。
- Users / use cases：訓練者自我檢視動作；作為 `video-understanding` 判斷層的一個新 domain；作為 `pose2sim` 的下游語意分析；作為其他 Python 專案可直接匯入的模組。

## Goals

- 從單機 2D 影片產出動作的自然語言描述，並允許使用者修正。
- 從影片產出自然語言的動作問題診斷。
- 將診斷結論映射到可檢索的肌群詞彙，或明確標記「無對應」。
- 從動作資料庫檢索出覆蓋所有弱點肌群的最小動作組合，並附上分步驟作法。
- 核心功能以純 Python 模組提供，不依賴任何介面層。
- 提供一個網頁介面作為預設操作方式，但核心可在不啟動介面的情況下使用。

## Inputs and Outputs

- Input：
  - 單機拍攝的人體動作影片。格式、長度上限、解析度下限待確認。
  - `exercises.json`（1,324 筆，約 17 MB，來自 exercises-dataset，版本以 commit 固定，取得方式見 `README.md`）。
  - 選填：使用者對動作描述的修正文字。
  - 選填：使用者可用器材清單（用於過濾處方）。
- Output：
  - 動作描述：自然語言（例如「一個負重深蹲」「一個側踢」）。不要求對應到資料庫的任何一筆動作。
  - 問題診斷：自然語言描述。
  - 弱點肌群：19 個 `target` 詞彙的子集，另附無法映射的原始詞清單。
  - 訓練處方：動作清單，每項含 `id`、`name`、`equipment`、覆蓋的肌群、`instruction_steps`。
- Error cases（內容層）：
  - 影片中無人 / 多人 / 人體大幅出框：回報無法分析，不輸出診斷。
  - 診斷結論無法映射到任何 `target`：明確列為「無對應動作」，不得以近似詞硬湊。
  - 動作含軀幹旋轉或身體離開拍攝平面：標記該項診斷不可靠。
  - 器材過濾後無可用動作：放寬限制並告知，或回報無法產出處方。
- Error cases（系統層）：
  - VLM 推論服務未啟動、連線失敗或推論逾時：回報服務不可用並指出是哪一階段失敗，不得回傳部分結果冒充完整輸出。
  - 影片格式不支援或解碼失敗：回報格式問題，不進入推論階段。
  - 上傳影片超過大小上限（200 MB）：在進入推論前拒絕並告知上限值。
  - `exercises.json` 不存在、無法解析或 schema 不符：啟動時即失敗並指出取得方式，不得在檢索階段才發現。
  - 前三階段已完成但處方檢索失敗：仍回傳已完成的診斷結果，並標明處方缺失原因。

## Scope

### In Scope

- 通用人體動作，不綁定領域（健身、武術、日常動作皆可輸入）。動作辨識不受資料庫內容限制。
- 單機 2D 影片輸入。
- VLM 驅動的動作描述、問題評估與成因推論。
- 診斷結論到肌群詞彙的約束映射層。
- 集合覆蓋式的處方檢索。
- 核心功能以純 Python 模組提供，可被其他專案直接匯入。
- FastAPI 服務層與網頁前端作為預設操作介面。
- 全本地推論，不呼叫雲端 API。

### Out of Scope

- 多機同步與 3D 三角測量（由 `pose2sim` 負責，本專案不重做）。
- 技術訓練與動作控制練習的推薦（資料庫沒有這類內容）。
- 訓練課表排程、週期化、負重與組次建議。
- 傷害診斷或任何醫療建議。輸出定位為訓練建議。
- 即時（real-time）分析。
- 使用者帳號、登入與多使用者資料保存。
- 資料庫媒體檔（圖片、GIF）的再散布。

## Requirements and Constraints

- Functional：
  - 動作辨識輸出自然語言描述，必須提供給使用者修正的機會，不得直接進入下游。
  - 動作辨識不得因為描述無法對應資料庫內容而中止流程。
  - 成因推論允許 VLM 自由生成，但進入處方檢索前必須經過約束映射。
  - 處方中的動作必須全部來自 `exercises.json` 且可由 `id` 驗證，不得由模型生成。
  - 處方必須附帶該動作的 `instruction_steps`。
  - 核心模組不得依賴 FastAPI、前端或任何 HTTP 相關套件。
  - 介面層不得包含業務邏輯，只做輸入輸出轉接。
- Performance：待確認。
- Correctness / reliability：
  - 處方動作必須可由 `id` 在 `exercises.json` 中驗證存在。
  - 系統不得對無法驗證的因果關係使用斷定語氣。
- Compatibility：
  - 輸入資料以 exercises-dataset 的 `exercises.json` schema 為準。
  - 核心模組必須可在無介面環境（腳本、其他專案）中使用。
  - 理解層與判斷層必須可分離，判斷層可替換為其他 domain。
- Security / privacy：影片可能包含可識別個人，不得寫入 repository，不得傳送至外部服務。網頁服務預設只綁定本機位址。

## Success Criteria

- [x] 端到端流程可執行：影片輸入 → 動作描述 → 診斷 → 弱點肌群 → 處方 + 作法。
- [x] 核心模組可在不啟動 FastAPI 的情況下由 Python 腳本完整呼叫。
- [x] 處方中 100% 的動作可在 `exercises.json` 中以 `id` 驗證存在。
- [x] 資料庫沒有的動作（如武術踢腿）輸入時，流程仍能完整產出診斷與處方。
- [x] 網頁介面可完成上傳、修正動作描述、檢視診斷與處方的完整操作（HTTP 層已實跑，
      瀏覽器端僅手動確認，未有自動化測試）。
- [x] 系統層錯誤（VLM 服務不可用、影片解碼失敗、資料檔缺失）皆有明確回報，不產生靜默失敗或部分結果。

驗證狀態與實際執行結果見 `docs/architecture.md` 的 Verification Status。

輸出品質的評估（診斷是否穩定、建議是否可執行）等實際輸出累積後再決定作法，不預先設計實驗與門檻。

## Open Questions

- [ ] 是否需要骨架（2D pose）作為 VLM 的輔助輸入？純 VLM 是否足以描述關節角度層級的問題。
- [ ] 影片取樣策略：目前為均勻取樣 6 張，實測會錯過關鍵動作。是否改為偵測畫面變化後取樣。
- [ ] `hip flexors` 等無對應 `target` 的肌群，是否需要補充外部動作來源。
- [ ] `SECONDARY_WEIGHT`（目前 0.25）是否合適，缺乏資料支持。
